# M0: prove the pipe

The first milestone, and the one that retires the most risk. The goal is narrow and concrete, so we can tell exactly when it is done.

## The goal

Take one pre-seeded two-player game, submit both players' orders, and have a containerized, headless copy of the engine generate exactly one turn from cloud storage and write each empire its own intel back. No accounts, no deadline clock, no AI, no web. Just the pipe: storage in, one turn, per-empire storage out.

When a developer can run this locally against a folder, and the same container can run it on GCP project `roybot` reading and writing GCS, M0 is done.

## What this milestone ships (in this repository)

The net-new code and infrastructure are written and committed. They are built against the real engine class shapes, so the port below has a fixed target to hit.

| Path | What it is |
|---|---|
| `ServerHost/Nova.Server.Host.csproj` | The headless host project (SDK-style, net10.0). References `Common` and `ServerState`. |
| `ServerHost/Program.cs` | Container entry point. `POST /internal/games/{id}/generate` and `GET /healthz`, plus a `generate <gameId>` CLI for local runs. |
| `ServerHost/Engine/TurnService.cs` | `GenerateTurnAsync(gameId)`: load state and orders, run `TurnGenerator.Generate()`, write state and intel back. Uses a scratch-directory shim so no engine internals change yet. |
| `ServerHost/Storage/IGameStore.cs` | The storage seam. |
| `ServerHost/Storage/LocalGameStore.cs` | Filesystem store for local development and tests. No cloud needed. |
| `ServerHost/Storage/GcsGameStore.cs` | GCS store for the cloud. |
| `ServerHost/Determinism/SeedDerivation.cs`, `NovaRandom.cs` | Deterministic seed derivation, so a turn is reproducible once the engine's RNG is seeded from it. |
| `ServerHost/Dockerfile` | Multi-stage build to a small Linux container. |
| `infra/terraform/*.tf` | The M0 infrastructure on `roybot`: image repo, three state buckets, a least-privilege service account, a private Cloud Run turn-generation service, Firestore for later. |
| `.github/workflows/build.yml` | Linux build and test, replacing the Windows-only Azure Pipelines. |

## The hard prerequisite: a headless port subset

None of the above compiles until `Common` and `ServerState` build on net10.0 without WinForms or `System.Drawing` on the turn path. That is the real work of M0, and it is deliberately scoped down: we only need enough of the port to generate a turn on an existing game. Full map generation (which is the heaviest `System.Drawing` user, in `StarMapInitialiser`) is exercised only when creating a new game, and M0 sidesteps that with a pre-made fixture (see below). So map-generation decoupling is not on the M0 path; the compile-level decoupling of the shared model is.

Ordered checklist for the M0 port subset:

1. Create SDK-style, net10.0 project files for `Common` and `ServerState`, and a `Galaxies.sln` that holds `Common`, `ServerState`, `ServerHost`, and `Tests`. Drop x86, the `USE_COMMAND_ORDERS` configuration, the ClickOnce and lock-file build hacks, and the legacy `ToolsVersion`.
2. Remove the `ControlLibrary` project reference from `ServerState` (`Server.csproj`). The turn engine must not reference a WinForms assembly.
3. Delete `Common/Serializer.cs` (dead `BinaryFormatter`) and the SOAP serialization reference; both fail to compile on modern .NET.
4. `Common/Report.cs`: replace the `MessageBox` calls with an `IReporter` sink (a static `Report.Sink` keeps the many call sites unchanged), and replace `Thread.CurrentThread.Abort()` with a thrown `NovaFatalException`. The host sets a logging sink; nothing pops a dialog.
5. `ServerState/Persistence/ServerData.cs`: remove `using System.Windows.Forms`, delete the `SaveFileDialog` branch in `Save()` (the host always sets `StatePathName`, so the dialog path is dead), and delete the eight-second file-lock retry loop in `Restore()`.
6. The shared model's `System.Drawing` split (design Section A.2): keep the string identifiers in `Common` (`ShipIcon.Source`, `Component.ImageFile`), move the live `Bitmap` properties and image loading out to the client presentation assembly. Do NOT add a reference to `System.Drawing.Common`; it is Windows-only on Linux and would fail at runtime, not build.
7. Headless content location: point the engine at `components.xml` (which ships in the container) through config, not through `FileSearcher`'s dialogs or the `nova.conf` registry path.

After this subset compiles on Linux, `ServerHost` compiles and `TurnService` runs.

## Determinism: seed before you port

The engine cannot be verified while it is non-deterministic, so this lands with the port, not after it.

1. Add `long MasterSeed` to `ServerData`, set at game creation and round-tripped through the existing `ToXml` and `XmlNode` constructor (add one `SaveData` line and one load case, and bump a `FormatVersion` on the state root).
2. In `TurnGenerator`, replace `rand = new Random()` (constructor) with `rand = NovaRandom.ForTurn(serverState.MasterSeed, serverState.TurnYear)`. When `SeedDerivation` and `NovaRandom` move from `ServerHost` into `Common` during the port, the engine can call them directly.
3. Replace every other unseeded `new Random()` with a derived stream, so no two subsystems share a sequence: `ServerState/BattleEngine.cs`, `ServerState/CheckForMinefields.cs`, `ServerState/NewGame/StarMapGenerator.cs`, `ServerState/NewGame/NameGenerator.cs`, the four instances in `ServerState/NewGame/StarMapInitialiser.cs`, and `Common/PointUtilities.cs` and `Common/SpaceAllocator.cs`. Use `NovaRandom.ForSubsystem(masterSeed, turnYear, "battle")` and friends. Prefer injecting the `Random` over newing one inside each class, so tests can substitute a recorded sequence.
4. Deterministic iteration: where a loop body mutates shared state or draws from the RNG, iterate collections sorted by key (empire id, star key, fleet key), not in raw dictionary order. `Generate()` iterates `AllEmpires.Values`, `IterateAllFleets()`, and `OwnedStars.Values`; .NET does not promise their order, and unordered iteration is a silent source of turn-to-turn divergence.

## The fixture: a pre-seeded two-player game

BUILT. `Tests/Fixtures/games/fixture-2p/state/current.sstate`, 164 KB: two empires
(Humanoid and Insectoid), 17 stars, three fleets and three designs each, at the
starting year 2100.

This section previously said to build the fixture with the desktop New Game
wizard on .NET Framework. That is not necessary. The wizard is only a front end
for `Gameinitializer`, which lives in `ServerState`, is part of the cloud
solution, and runs headless. The fixture is now generated on Linux by
`Tests.ServerHost/FixtureBuilder.cs`, an `[Explicit]` test that CI never runs:

```
dotnet test Tests.ServerHost -c Release --filter "FullyQualifiedName~BuildFixture"
```

The unseeded map RNG does not block this. Unseeded generation is a problem for
REPRODUCING a game, not for producing one artifact once: the builder runs a
single time and its output is committed. Seeding is still required before the
server can create games on demand, and it is still open.

The fixture holds no orders. Orders are per turn year and per empire, so they
belong to a run rather than to the game; `TurnRunTests` writes them as part of
the test that needs them.

### Layout

The fixture uses the canonical layout in `ServerHost/Storage/IGameStore.cs`
(`GamePaths`), which is the same layout `LocalGameStore`, `GcsGameStore`, and
galaxies-api all use:

```
<root>/games/fixture-2p/state/current.sstate
<root>/games/fixture-2p/state/{turnYear}.sstate
<root>/games/fixture-2p/orders/{turnYear}/{empireId}.orders
<root>/games/fixture-2p/intel/{turnYear}/{empireId}.intel
<root>/games/fixture-2p/backup/{turnYear}/
```

Objects are keyed by empire id, not race name. Race names are player-supplied
strings: they carry spaces and punctuation, they are not unique, and a player can
change one. The engine still reads and writes `{raceName}.orders` and
`{raceName}.intel` inside its own game folder; translating between the two is the
game store's job, which is why the download is two calls (state first, then
orders) rather than one. The roster and the turn year both come from the loaded
state.

An earlier version of this document described a flat `state.sstate` plus
`orders/<race>.orders`. That layout disagreed with what galaxies-api writes, and
the disagreement was the defect: the API wrote orders to one path, the game store
read another, and turns generated with every submitted order silently discarded.

## Running it locally

```
export GALAXIES_LOCAL_ROOT=/path/to/root
cp -r Tests/Fixtures/games "$GALAXIES_LOCAL_ROOT/"
dotnet run --project ServerHost -- generate fixture-2p
```

The host copies the state into a scratch directory, loads it, stages each seat's
orders under the name the engine opens, points the engine's `GameFolder` at that
directory, runs `TurnGenerator.Generate()`, writes the new state and one `.intel`
per empire back, and prints the new turn year. That is the whole pipe, on one
machine, no cloud.

Verified output, no orders submitted:

```
Staged 0 of 2 orders files for game fixture-2p, year 2100
Generated turn for fixture-2p: new year 2101

games/fixture-2p/backup/2100/fixture-2p.sstate
games/fixture-2p/intel/2101/1.intel
games/fixture-2p/intel/2101/2.intel
games/fixture-2p/state/2101.sstate
games/fixture-2p/state/current.sstate
```

`Nova error: Unable to locate Nova! graphics components.` on that run is correct
and expected: the graphics database failing to load headless is the point of the
port.

## Deploying to roybot

```
# 1. Build and push the image
gcloud auth configure-docker us-central1-docker.pkg.dev
docker build -f ServerHost/Dockerfile -t \
  us-central1-docker.pkg.dev/roybot/roybot-galaxies/galaxies-turngen:0.1.0 .
docker push us-central1-docker.pkg.dev/roybot/roybot-galaxies/galaxies-turngen:0.1.0

# 2. Provision infrastructure (create the tfstate bucket by hand first)
cd infra/terraform
terraform init -backend-config="bucket=roybot-galaxies-tfstate"
terraform apply -var="turngen_image=us-central1-docker.pkg.dev/roybot/roybot-galaxies/galaxies-turngen:0.1.0"

# 3. Upload the fixture to the state and orders buckets, then call the private
#    service with an identity token (it is internal-only, no public access).
```

## The acceptance test

A golden-turn regression, run in CI:

1. Capture the golden first: with the RNG seeded, run `Generate()` on the fixture on the current .NET Framework build and commit the resulting `state.sstate` as the expected output.
2. Prove it reproduces on the target: run the same seeded generation on x64 Linux net10.0 and assert the output matches. If floating-point in battle or movement math diverges across architecture, re-baseline the golden on the Linux target and pin the engine version per game. This spike is the single most important check in M0, because it is where a silently different game would first show.
3. The test reuses `SimpleTurnGenerator` from the `Tests` project, which already subclasses `TurnGenerator` and overrides the file seams, so the harness exists.

CI (`.github/workflows/build.yml`) restores, builds, and runs the suite on `ubuntu-latest`. It is red until the port subset compiles, which is the correct signal.

## What M0 does not include

Named here so the scope stays honest:

- No authentication. The generate endpoint is private and called by hand or by a test.
- No scheduler, no deadlines, no "maximum time between turns" (that is M2).
- No AI participants (M3).
- No cloud game creation, so no map generation on the server path (a fixture stands in).
- No public site, lobby, or web client.

### What closing criterion 2 turned up

Four defects, none of which any existing test could see, all of which degraded
play silently rather than crashing. They are recorded here because they are the
argument for finishing M0 before building on top of it.

1. **Orders were never read.** Three components used three different paths and two
   different filename conventions. Fixed by the canonical layout above.
2. **Intel was never delivered.** `IntelWriter.WriteIntel()` reassigned
   `serverState.GameFolder` from a discovered Nova root on every empire, so intel
   was written outside the working directory the store uploads from, and
   `CleanupOrders`, which runs after it, then used the wrong folder too.
3. **No saved game containing a fleet could be loaded headless.**
   `AllShipIcons.GetIconBySource` fell back to `Data.IconList[0]` when a hull was
   missing from the graphics database. On a server that list is empty, so it
   threw, and `FleetIntel(XmlNode)` turns any exception into a fatal error. Every
   game has fleets from turn one. This is the same family as the two `ShipDesign`
   bugs M3 fixed, one call site over.
4. **Every game reported GAME OVER after its first turn.** `GameInProgress` was
   set to true only by the desktop console, which is not part of the server build,
   so `TurnService`'s `gameEnded = !GameInProgress` was always true. Fixed in
   `Gameinitializer`.

### What the first real container run turned up

The four above were found by running a turn locally. Building and running the
actual images found three more that a local run cannot see, which is the argument
for closing criterion 3 rather than trusting a green test suite.

5. **All four images failed to build.** `Common.csproj` and `Server.csproj`
   compile the repository-root `VersionInfo.cs` by link, and no Dockerfile copied
   it, so restore succeeded and publish failed with CS2001 everywhere. Separately,
   `.dockerignore` excluded `Nova/` while the participant Dockerfile copied it.
   `Tests.ServerHost/DockerContextTests.cs` now checks the copy lists against the
   linked files, in CI, with no Docker daemon.
6. **The container could not find `components.xml`.** `AllComponents.Restore()`
   resolved through `FileSearcher`, which searches nova.conf, the registry, a Nova
   root, and finally a file dialog. A container has none of those, so
   `EmpireData.Initialize()` threw and no game could be loaded, even though
   `components.xml` was sitting at `/app/components.xml`. It now honours
   `GALAXIES_COMPONENT_FILE` and then a `components.xml` beside the assembly. The
   local run passed only because ambient config supplied a path.
7. **Empty strings in `appsettings.json` defeated every `??` fallback.** The file
   ships each `GALAXIES_*` key as `""` to document it, and `""` is not null, so
   the fallback never fired. In turngen, `ScratchRoot` became `""`, which made the
   scratch path relative, which resolved against the image's `/app` working
   directory, which the non-root user cannot write: every HTTP generate returned
   500 while the CLI kept working. In the API it was worse. `GALAXIES_JWT_SIGNING_KEY`
   resolved to `""`, so the service would have signed and validated every session
   token with an empty HMAC key rather than with the documented dev placeholder.
   Both now treat blank as absent, and the API refuses to start outside
   Development without a real signing key and Google client id.

A minor eighth: `galaxies-ai`'s `/readyz` returned 500 rather than 503 when
Firestore was unreachable, because resolving the store threw before the ping could
report failure. That is the exact condition the probe exists to report, and the
platform reads 503 as "not ready, retry" but 500 as "broken handler".

A ninth is filed and not fixed: `VictoryCheck.Victor()` only appends a text
message and sets no flag, so nothing machine-readable says a game ended or who
won, yet `GenerationOutcome.GameEnded`, `GenerationCommit.WinnerEmpireId`, and
M4's game-over route all depend on it. With defect 4 fixed, `GameEnded` is now
permanently false rather than permanently true. Deciding what ends a game is a
product call and should not be invented during M0.
